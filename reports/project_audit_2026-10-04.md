## 3. Критичні проблеми — P0

### F01. Маршрути учня не перевіряють право на спробу

**Відтворено.** [student.py](../app/routes/student.py), рядки 128, 174, 265, 332, 385, 419. Залежність `get_current_attempt` імпортована, але не використовується в цих маршрутах. Ідентифікатор у URL є фактично єдиною умовою доступу.

Без cookie отримано HTTP 200 для сторінки проходження, збереження відповіді та завершення чужої синтетичної спроби. Крім того, повторний вхід із таким самим ПІБ і кодом видає cookie вже наявної спроби: ПІБ працює як посвідчення особи.

**Виправлення:** для кожної операції читати підписану cookie, звіряти її спробу з `attempt_id` і перевіряти стан. Відновлювати спробу тільки за вже наявною авторизацією або окремим випадковим токеном/підтвердженням учителя. Самих випадкових ID недостатньо.

**Критерій:** анонімний клієнт і cookie іншого учня не можуть переглядати, змінювати, завершувати спробу чи писати її події; ПІБ іншого учня не дозволяє отримати його сесію.

### F02. Правильні відповіді зберігаються в публічному `test.json`

**Відтворено.** [test_file_service.py](../app/services/test_file_service.py), рядки 69–118; [main.py](../app/main.py), рядок 82. `save_test_locally()` записує повну структуру тесту, включно з `is_correct`, у `app/static/tests/<folder>/test.json`. Увесь `/static` доступний без авторизації.

GET синтетичного `test.json` без cookie повернув HTTP 200 з позначками правильних відповідей. Папку можна визначити з URL зображень, якщо вони є в тесті; відсутність directory listing не захищає від відомого шляху. До цих файлів також застосовується публічне кешування на добу.

**Виправлення:** перенести повні JSON-файли до приватного каталогу даних; експортувати їх лише через авторизований маршрут учителя. Публічно видавати тільки необхідні медіафайли. Видалити старі публічні копії й урахувати вже закешовані матеріали.

**Критерій:** отримати файл із ключами через `/static` неможливо; авторизований експорт працює.

### F03. Payload сторінки учня містить ключі відповідей

**Відтворено.** [test_service.py](../app/services/test_service.py), рядки 110–152. Навіть після закриття `test.json` витік збережеться: payload передає всі `option_text`, правильні `matching_text` і `order_index`.

Для `short_text` це текст очікуваної відповіді, для `matching` — правильні пари, для `sequence` — порядок, для `hotspot` — координати області. Перемішування не приховує ключ, коли поряд із ним передаються вихідні метадані.

**Виправлення:** створити окрему схему представлення для учня. Для короткої відповіді не передавати еталонні варіанти; для відповідностей передавати незалежні колонки без правильних пар; для послідовності — перемішані елементи без правильних індексів; для hotspot — лише зображення. Ключі залишити на сервері.

**Критерій:** HTML, JSON і мережеві відповіді учня до завершення не дозволяють відновити ключі; усі типи питань залишаються придатними до проходження.

### F04. Експорт тесту може читати файли поза папкою зображень

**Відтворено.** [teacher.py](../app/routes/teacher.py), рядки 1965–2004. Експорт будує шлях через `os.path.join("app", url.lstrip("/"))` без перевірки допустимого кореня. `image_url` можна задавати у питаннях.

За `image_url="../audit-marker.txt"` експорт повернув вміст власного маркера з кореня тимчасового середовища у Base64. За наявності доступу до відповідного файлу аналогічний шлях може відкрити конфігурацію чи інші серверні дані. Реальні секрети не читалися.

**Виправлення:** зберігати посилання на медіа як контрольовані сервером ID; для файлового доступу перевіряти `resolve()` і належність дозволеному медіакаталогу, включно із symlink. Не приймати довільні шляхи, абсолютні URL або `..` як локальні файли.

**Критерій:** експорт відхиляє посилання поза дозволеним коренем і вбудовує тільки медіа цього тесту.

## 4. Проблеми високого пріоритету — P1

### F05. API та WebSocket доступні без авторизації

**Відтворено.** [api.py](../app/routes/api.py), рядки 10, 46, 64; [websocket.py](../app/routes/websocket.py), рядки 8, 31. API видає ПІБ, бали, ID спроб і код доступу; WebSocket приймає клієнта до перевірки користувача або існування сесії.

Анонімний `/api/session-status/<id>` повернув ПІБ і код. Обидва WebSocket прийняли навіть неіснуючий ID. Монітор може розкривати коректність відповідей під час тесту. Сторонній student WebSocket може витіснити справжній канал, бо менеджер зберігає один socket на ID спроби.

**Виправлення:** додати авторизацію та перевірку власника до API і перед `websocket.accept()`, перевіряти Origin. Для student-каналу звіряти cookie спроби. При відключенні видаляти саме відповідний socket; визначити політику кількох вкладок.

**Критерій:** чужі та анонімні підключення відхиляються; повторне підключення учня не втрачає команд учителя.

### F06. Можна додати відповідь на питання іншого тесту

**Відтворено.** [student.py](../app/routes/student.py), рядки 281–308; [crud.py](../app/crud.py), рядок 330; [test_service.py](../app/services/test_service.py), рядок 13.

`question_id` не перевіряється на належність тесту й призначеному набору. Якщо відповідей ще немає, одна стороння відповідь стає набором питань спроби: `get_attempt_questions()` відновлює його зі збережених відповідей. У перевірці чужому питанню призначено 100 балів; спроба завершилася з 100/100.

**Виправлення:** фіксувати призначений набір на старті в окремій структурі й приймати відповіді лише на ці питання; перевіряти належність option ID питанню. Непризначене питання не повинно створювати рядок відповіді.

**Критерій:** сторонні, виключені та непризначені питання відхиляються без зміни знаменника оцінки.

### F07. Час і життєвий цикл недостатньо контролюються сервером

**Відтворено та підтверджено кодом.** [student.py](../app/routes/student.py), рядки 242, 265, 332; [student.js](../app/static/js/student.js), рядки 779–876, 1007. Відповідь прийнято через 60 хвилин за ліміту 1 хвилина навіть у закритій сесії.

Таймер питання скидається на клієнті; пауза/офлайн зупиняють браузерний таймер, тоді як сервер рахує звичайний час від `started_at`. `autoSubmitTimeout()` викликає завершення без `timeout=true`, і прострочена спроба отримує `finished`. Сервер не визначає timeout самостійно.

**Виправлення:** зберігати серверний дедлайн, тривалість паузи й дедлайн питання; перевіряти їх при кожному записі. Установити однозначні дозволені переходи станів та правило поведінки при закритті сесії. Timeout визначати за серверним часом.

**Критерій:** F5, зміна JavaScript і прямі запити не продовжують час; пауза узгоджена після перезавантаження; прострочення має статус `timeout`.

### F08. Невалідна відповідь спочатку зберігається, потім спричиняє 500

**Відтворено.** [student.py](../app/routes/student.py), рядки 277–308; [result_service.py](../app/services/result_service.py), рядок 96; [crud.py](../app/crud.py), рядок 330.

За `selected_options=123` оцінювання впало з TypeError, але JSON `123` уже був закомічений. Наступна коректна відповідь отримала 400 як повторне збереження. Перевірки також не задають строгих типів/меж для тексту, координат, балів і структури питань.

**Виправлення:** використовувати Pydantic-схеми для кожного типу питання, перевіряти всі значення до запису й оцінювати в одній транзакції. Неправильний запит має давати 400/422 без збереження. Передбачити відновлення вже пошкоджених відповідей.

**Критерій:** числа замість списку, чужі option ID, некоректні координати та надмірні дані не дають 500 і не блокують подальшу правильну відповідь.

### F09. Небезпечне вставлення JSON/URL у HTML створює ризик XSS

**Частково відтворено:** неекранований закривальний тег `</script>` повертається в HTML редактора. Виконання JavaScript у браузері не перевірялося. [edit_test.html](../app/templates/edit_test.html), рядок 166; [teacher_dashboard.html](../app/templates/teacher_dashboard.html), рядки 324–329; [student.js](../app/static/js/student.js), рядки 286, 420; [teacher.js](../app/static/js/teacher.js), рядок 475.

Серіалізований рядок із `|safe` може закрити `<script type="application/json">`; URL зображень підставляються в `innerHTML` без належного контролю. Імпортований сторонній тест є реальним джерелом цих даних.

**Виправлення:** передавати словник у шаблон і застосовувати `tojson`; задавати DOM-атрибути через DOM API, перевіряти схему та джерело URL. Додати CSP як додатковий захист. Рекомендації спираються на [OWASP XSS Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html).

**Критерій:** імпортований текст із HTML/закривальними тегами відображається як дані; атрибути зображень не створюють обробників подій.

### F10. Завантаження «зображення» допускає чужий тест та HTML

**Відтворено.** [teacher.py](../app/routes/teacher.py), рядки 2018–2054. Перевіряється наявність тесту, але не `teacher_id`; немає дозволеного списку форматів, перевірки вмісту чи прикладного ліміту розміру.

Учитель завантажив нешкідливий `.html` у папку тесту іншого вчителя. Файл видався анонімно як `text/html` з того самого origin. Довільні активні файли також можна вкладати в JSON-імпорт як embedded images.

**Виправлення:** перевіряти власника тесту/сесії завантаження, дозволяти тільки необхідні формати й перевіряти фактичний вміст; обмежувати обсяг і кількість файлів. Активні формати заборонити або ізолювати; додати очищення тимчасових файлів. Див. [OWASP File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html).

**Критерій:** чужий тест, HTML/SVG зі скриптами та надмірні файли відхиляються; валідні зображення проходять.

### F11. Відомий fallback `SECRET_KEY` дозволяє підробити cookie

**Аналіз коду; залежить від конфігурації розгортання.** [config.py](../app/config.py), рядок 17; [.env.example](../.env.example); [security.py](../app/security.py), рядки 49, 68, 104; [api_client.py](../gui/api_client.py), рядок 24.

Значення за замовчуванням відоме з коду; застосунок не відхиляє його. Якщо оператор пропустить заміну, можна підписувати teacher/student cookie. Сам факт наявності цього fallback не доводить, що робочий сервер використовує його: секрет із локального `.env` не перевірявся. Після зміни пароля старі teacher-cookie також не відкликаються.

**Виправлення:** перевіряти на старті наявність випадкового ключа й відхиляти шаблонне значення; для локального першого запуску безпечно генерувати та зберігати окремий ключ. Додати версію сесії або серверне сховище сесій для відкликання; під HTTPS ставити `Secure`.

**Критерій:** сервер не стартує з небезпечним ключем; після скидання пароля попередня сесія не працює.

### F12. Оновлення схеми БД ненадійне й неповне

**Аналіз коду.** [main.py](../app/main.py), рядки 20–49. `create_all()` не оновлює наявні таблиці; вручну додаються тільки три колонки. Наприклад, `folder_name`, `is_pinned`, `max_grade` та інші поля не покриваються цим механізмом.

Після помилки `ALTER TABLE` немає rollback; для PostgreSQL наступні команди в цій транзакції не зможуть нормально виконатися. `BOOLEAN DEFAULT 0` орієнтовано на SQLite. Також будь-який `DATABASE_URL` перетворюється на файловий шлях: PostgreSQL URL може спричинити створення зайвих каталогів із частинами реквізитів.

**Виправлення:** запровадити версійні Alembic-міграції для обох БД, перевірити upgrade зі старої схеми; працювати з SQLite-шляхом тільки після розбору типу URL. Не приховувати помилки міграцій. Автогенерація потребує перегляду: [Alembic](https://alembic.sqlalchemy.org/en/latest/autogenerate.html).

**Критерій:** upgrade старої бази відтворюваний, перевірений на обох рушіях і не маскує помилок.

### F13. Перенесення SQLite → PostgreSQL не гарантує безпечний результат

**Аналіз коду і README; PostgreSQL не запускався.** [migrate_sqlite_to_postgres.py](../scripts/migrate_sqlite_to_postgres.py), рядки 21–80.

Проблеми: URL з hostname `postgres` із прикладу `.env` призначено для Docker-мережі, але команду пропонують запускати на хості; URL з паролем друкується; наявні дані цілі видаляються без підтвердження/backup; порожні таблиці джерела залишають старі дані цілі; явні ID вставляються без синхронізації sequences; зображення/результати не переносяться у томи. Вимкнення тригерів через `session_replication_role` ускладнює контроль цілісності та потребує відповідних прав.

**Виправлення:** явно задавати джерело/ціль, запускати у правильній мережі або задавати host URL; маскувати реквізити; за замовчуванням вимагати порожню ціль. Мігрувати транзакційно в порядку залежностей без вимкнення перевірок, відновлювати sequences і переносити файли. Перевіряти кількість рядків, зв'язки та контрольні результати. Для sequences див. [PostgreSQL](https://www.postgresql.org/docs/16/functions-sequence.html).

**Критерій:** після міграції створюється новий учитель/тест без конфлікту ID; зображення доступні; помилка не залишає частково перенесені дані.

### F14. Backup/restore/update не забезпечують заявленого відновлення

**Аналіз скриптів; руйнівні команди не запускалися.** [backup.sh](../scripts/backup.sh), [restore.sh](../scripts/restore.sh), [update.sh](../scripts/update.sh).

Backup знімає БД і файли послідовно, поки застосунок може змінювати їх. Не охоплює `static/uploads`. Restore продовжується після невдалого захисного backup; копіювання накладає файли поверх наявних, залишаючи зайві; немає перевірки архіву до видалення БД чи відновлення запуску через trap. Update продовжується після невдалого `git pull` і не перевіряє HTTP-готовність. Відновлення БД не повертає попередню версію коду/образу, хоча README описує це як rollback.

**Виправлення:** створювати узгоджений snapshot БД і всіх файлових сховищ; додати manifest із версією коду/схеми та checksum. Перед restore перевіряти артефакти; зупинятися при невдалому захисному backup; відновлювати файли через staging із заміною і керувати запуском у trap. Оновлюватися лише після успішного отримання коду та readiness-check; зберігати попередній image/tag.

**Критерій:** повне відновлення перевірене в окремому середовищі, включно зі зникненням зайвих файлів і поверненням сумісної версії застосунку.

### F15. Редагування тесту змінює оцінювання вже розпочатих спроб

**Відтворено; видалення історичних відповідей підтверджено кодом.** [crud.py](../app/crud.py), рядки 143–197; [result_service.py](../app/services/result_service.py), рядок 218; [teacher.py](../app/routes/teacher.py), рядок 488.

Спроба посилається на живі питання й варіанти. Зміна балів питання з 1 до 50 змінила повторне оцінювання з 1/5 до 50/54 без зміни відповіді. Видалення питання в `update_test()` прямо видаляє пов'язані `StudentAnswer`, зокрема історичні. Зміна варіантів також може знецінити збережені option ID.

**Виправлення:** створювати незмінну версію тесту на сесію або snapshot питань, ключів і балів. Як короткостроковий захід заборонити зміни тесту з активними/історичними спробами й пропонувати копію.

**Критерій:** редагування нового варіанта тесту не змінює минулі результати та деталізацію.

### F16. Нормалізація тексту неправильно оцінює числа

**Відтворено.** [result_service.py](../app/services/result_service.py), рядки 9–16, 109–129. Нормалізація видаляє знак мінус і десятковий роздільник. Відповіді `5` для еталона `-5` та `15` для еталона `1.5` отримали повний бал; другий випадок перевірено з вимкненим fuzzy matching.

**Виправлення:** розділити правила текстових і числових відповідей. Для чисел зберігати знак, коректно розбирати кому/крапку та допустиму похибку; для тексту не видаляти значущі математичні символи. Fuzzy matching не застосовувати до чисел автоматично; підтримати всі дозволені еталонні відповіді.

**Критерій:** знак і десяткова позиція впливають на результат; правила нечіткого порівняння зрозумілі вчителю.

### F17. Перший користувач не стає адміністратором за довільного логіна

**Відтворено.** [setup.py](../app/routes/setup.py), рядки 68–102; [teacher.py](../app/routes/teacher.py), зокрема рядки 2112, 2178, 2263. Роль визначається через `username == "admin"`, а майстер дозволяє інший логін.

Перший користувач `owner` успішно створений, але створення іншого вчителя йому заборонено. Вебінтерфейс не дає відновити адміністраторські права. Під час першого запуску доступний будь-кому `/setup`; ризик перехоплення початкового налаштування залежить від відкритості мережі.

**Виправлення:** додати явну роль `admin/teacher` і автоматично призначати її першому користувачу незалежно від логіна. Початкове налаштування захистити одноразовим токеном або локальним доступом; створення першого користувача зробити атомарним.

**Критерій:** будь-який дозволений логін першого користувача має належні права, наступні користувачі — тільки призначену роль.

## 5. Проблеми середнього пріоритету — P2

### F18. Checkbox приховування результатів не працює

**Відтворено.** [teacher.py](../app/routes/teacher.py), рядки 399, 504; [edit_test.html](../app/templates/edit_test.html), рядок 75. Невідмічений checkbox не передається браузером, але `Form(True)` повертає true. Після редагування тесту з прихованими результатами значення стало true.

**Виправлення:** для обробки checkbox використовувати false за відсутності поля або явну булеву JSON-схему; початкову відмітку задавати тільки в UI. **Критерій:** зняття checkbox зберігає false, учень не бачить результат.

### F19. JSON-обмін втрачає налаштування

**Відтворено.** [import_export_service.py](../app/services/import_export_service.py), рядки 48–54; [teacher.py](../app/routes/teacher.py), рядок 1914; [test_file_service.py](../app/services/test_file_service.py), рядок 69.

Після експорту й імпорту `time_limit_per_question=10` став null, `max_grade=5` став 12, `allow_retake`, `allow_partial_grading` і `use_fuzzy_matching` стали false. Експорт і локальний JSON мають різний набір полів; частину не експортують, частину ігнорують при імпорті. Імпорт також перезаписує предмет даними профілю.

**Виправлення:** єдина версійна схема обміну, одна реалізація серіалізації, правила сумісності старих файлів і явний вибір заміни предмета/класу. **Критерій:** повний round trip зберігає налаштування, всі типи питань і медіа.

### F20. Цілісність БД і захист від паралельного запису недостатні

**`PRAGMA foreign_keys=0` відтворено; конкурентні гонки — висновок із коду.** [database.py](../app/database.py), рядки 20–28; [models.py](../app/models.py), рядок 202; [student.py](../app/routes/student.py), рядок 284.

SQLite не вмикає зовнішні ключі. Немає `UNIQUE(attempt_id, question_id)`, а захист від перездачі є послідовністю читання і запису. На кількох процесах/паралельних підключеннях можливі дублікати або перезапис. Успішна перевірка повторного послідовного запиту не доводить атомарності.

**Виправлення:** після перевірки наявних даних увімкнути foreign keys, додати унікальне обмеження та атомарне умовне оновлення незаповненої відповіді. Генерація коду доступу має враховувати унікальність серед усіх сесій, включно із закритими, і повторювати спробу після конфлікту. Див. [SQLAlchemy: SQLite foreign keys](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html#foreign-key-support).

**Критерій:** два одночасні записи створюють одну остаточну відповідь; сторонні посилання відхиляються БД.

### F21. Синхронна робота блокує async-маршрути; оцінювання робить зайві commit

**Аналіз коду; навантаження не вимірювалося.** [teacher.py](../app/routes/teacher.py), [result_service.py](../app/services/result_service.py), рядок 218; [crud.py](../app/crud.py), рядок 365; [logger_service.py](../app/services/logger_service.py).

У `async def` виконуються синхронні SQLAlchemy-запити, PBKDF2, обробка DOCX/XML, файлові операції й `subprocess.run`. Оцінювання кожної відповіді окремо виконує commit/refresh. При одночасному тестуванні це може затримувати WebSocket та інші запити. Частина сторінок робить N+1-запити та пагінацію вже після завантаження всіх результатів.

**Виправлення:** винести блокувальні операції в контрольований thread pool або перейти на async-драйвер; узгодити життєвий цикл Session. Оцінювати спробу в одній транзакції, застосувати eager loading та SQL-пагінацію. Рекомендація відповідає [FastAPI: async і sync](https://fastapi.tiangolo.com/async/).

**Критерій:** виміряний сценарій для очікуваного класу користувачів, із лімітами часу відповіді й без втрат команд паузи/зупинки.

### F22. Production-конфігурація потребує зміцнення

**Аналіз файлів.** [compose.yaml](../compose.yaml), [Dockerfile](../Dockerfile), [run.py](../run.py).

PostgreSQL публікується на `5432` без обмеження host IP; є fallback пароля `postgres`. Dockerfile запускає застосунок від root і не встановлює `zip`, потрібний архівуванню логів. `static/uploads` не має окремого persistent volume і не входить до backup. Відсутні readiness/liveness для app; `run.py` безумовно вмикає reload.

**Виправлення:** прибрати зовнішній порт БД або обмежити його localhost для необхідних операцій; вимагати задані реквізити. Запускати app від окремого користувача, покрити всі робочі файли томами й backup, додати health/readiness, вимикати reload у робочому режимі. Для мережевого доступу застосувати HTTPS, CSRF-захист форм, перевірку Origin та обмеження частоти входів. Правила публікації портів: [Docker Compose](https://docs.docker.com/reference/compose-file/services/#ports).

**Критерій:** перезбирання контейнера не втрачає файлів; стан «готовий» означає доступність app і БД; БД не відкрита ширше необхідного.

### F23. GUI має іншу модель доступу і частково прив'язаний до SQLite

**Аналіз коду; GUI не запускався.** [session_manager.py](../gui/session_manager.py), рядки 6–15; [register_window.py](../gui/register_window.py), рядки 127, 423, 465; [api_client.py](../gui/api_client.py).

Менеджер сесій відкриває конкретний SQLite-файл, незалежно від `DATABASE_URL`, тоді як реєстрація використовує SQLAlchemy. Після переходу на PostgreSQL частини GUI можуть показувати різні дані. GUI керує користувачами без вебавторизації; ApiClient сам підписує cookie довільного вчителя локальним ключем. На чистій БД реєстрація сама не виконує створення таблиць.

**Виправлення:** або явно обмежити GUI локальним SQLite-режимом і довіреним оператором, або перевести його на авторизований API зі спільними правилами ролей. Не роздавати серверний ключ для клієнтської авторизації; додати перевірку готовності БД.

**Критерій:** документація чітко визначає підтримувані режими; усі частини GUI читають ту саму БД і дотримуються узгодженої моделі доступу.

### F24. Події fullscreen губляться; архівування логів має приховану залежність

**Невідома подія відтворена; решта — аналіз коду.** [student.js](../app/static/js/student.js), рядки 934, 943, 971; [models.py](../app/models.py), рядок 45; [logger_service.py](../app/services/logger_service.py), рядок 108.

Клієнт надсилає `fullscreen_exit`, `fullscreen_timeout_fail`, `fullscreen_return`, яких немає в EventType; сервер відповідає `unknown_event`. Архіватор викликає зовнішній `zip -P`, не встановлений Dockerfile і не гарантований на Windows; пароль адміністратора передається аргументом процесу. Логи браузера при цьому залишаються даними від недовіреного клієнта.

**Виправлення:** узгодити перелік і права на події, відокремити серверні lifecycle-події від клієнтської телеметрії. Обрати підтримувану кросплатформну реалізацію архівування, не передавати пароль облікового запису через argv й перевіряти архів до видалення джерела.

**Критерій:** документовані події зберігаються й показуються; архівування та читання перевірені на підтримуваних платформах.

### F25. Документація, залежності й перевірки не підтримують відтворюваний реліз

**Аналіз репозиторію та середовища.** [README](../README.md), [requirements.txt](../requirements.txt), [.gitignore](../.gitignore).

Залежності задані тільки нижніми межами `>=`; немає lockfile, видимого CI та відстежуваного тестового набору. Локальні пробні тести лежать у `scratch/`, який ігнорується Git. Вони не покривають основні знайдені сценарії. Ruff-зауваження переважно не є функціональними дефектами; їх варто виправляти після P0/P1.

README називає Linux launcher запуском сервера, хоча він відкриває GUI; не містить повного Linux bootstrap; обіцяє автономність, але dashboard завантажує Chart.js із CDN. Інструкція перенесення на новий ПК не включає код `app/`/requirements або готовий image і запускає лише postgres перед restore, який потребує контейнера app. Заявлений rollback не повертає код. Заявлена MIT-ліцензія не підкріплена окремим LICENSE у Git.

**Виправлення:** зафіксувати перевірені залежності й підтримувані Python/OS, розділити server/gui/dev requirements; додати CI й тести ключових сценаріїв. Переписати інструкції для чистого встановлення, міграції, перенесення та rollback за реально перевіреною процедурою; зберігати Chart.js локально. Додати відповідний LICENSE, якщо MIT справді є наміром власника.

**Критерій:** новий клон встановлюється й проходить перевірки за документацією; основні сторінки працюють без інтернету.

## 7. Перевірки після виправлень

Першочерговий тестовий набір має перевіряти поведінку, важливу для користувача:

1. Матрицю доступу: anonymous, власний/чужий учень, власний/чужий учитель, admin, деактивований користувач; HTTP і WebSocket.
2. Відсутність ключів у всіх відповідях учню та публічних файлах, включно з медіа й кешуванням.
3. Вісім типів питань: коректні/неправильні відповіді, невалідні типи, від'ємні та дробові числа, часткові бали, альтернативні еталони.
4. Час, паузу, закриття сесії, F5, офлайн, відновлення зв'язку, повторний і одночасний запис.
5. Редагування/видалення після тестування та незмінність історичних результатів.
6. JSON round trip усіх налаштувань і медіа, контрольні DOCX/XML, безпечну обробку імпорту й завантажень.
7. Чисте встановлення й upgrade старої SQLite/PostgreSQL; повне відновлення, перенесення і rollback.
8. Очікуване навантаження одного класу, автономну роботу frontend і smoke-перевірки підтримуваних GUI-платформ.

## 8. Артефакти й відтворення

- [Скрипт контрольних спостережень](audit_checks.py).
- [Машиночитані результати](audit_results_2026-10-04.json).

Запуск із кореня проєкту:

```bash
PYTHONDONTWRITEBYTECODE=1 .venv/bin/python reports/audit_checks.py
.venv/bin/ruff check --isolated --select E9,F63,F7,F82 app gui scripts run.py run_gui.py run_register.py
.venv/bin/ruff check --isolated --select F app gui scripts run.py run_gui.py run_register.py
bash -n scripts/backup.sh scripts/restore.sh scripts/update.sh start_linux.sh start_register.sh
docker compose config --quiet
```

Скрипт явно підміняє DATABASE_URL і SECRET_KEY тестовими значеннями та змінює робочу директорію на `TemporaryDirectory`; робоча база не використовується. Поле `reproduced=true` означає, що спостереження в назві перевірки підтвердилося: для `fresh_start`, `deterministic_payload`, `sequential_resubmit_blocked`, `sample_xml_import` і `sample_docx_import` це позитивна поведінка, для інших — відтворений дефект. Це матеріал аудиту, а не готова regression suite: після виправлень очікування треба перетворити на тести безпечної поведінки.

У sandbox додано короткий asyncio ticker для коректного пробудження event loop після роботи потоку; код застосунку та його залежності не підміняються. Для production-висновків усе одно потрібні окремі перевірки на підтримуваному Python 3.11 і реальному PostgreSQL.
