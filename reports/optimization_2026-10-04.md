# Виконані оптимізації SchoolTest

Дата: 4 жовтня 2026 року. Зміни внесено до робочого дерева; розгортання, Git-коміт і зміни робочих даних не виконувалися. Первинний [аудит](project_audit_2026-10-04.md) описує ревізію `b6d74a8` до цих змін.

## Сценарій користувача

Учень вводить ПІБ; клас визначається тестом учителя. Старт потребує натискання кнопки fullscreen. Вихід із fullscreen/перемикання вікна дає попередження та відлік, три порушення завершують спробу. Якщо тест дозволяє повторне проходження й сесія відкрита, повторна спроба використовує той самий ПІБ.

Під час втрати зв’язку збереження відповідей має залишатися зрозумілим учню: локальна копія відрізняється від підтвердження сервером. Пріоритет інтерфейсу вчителя, уточнений користувачем: **список тестів і керування сесіями**.

## Що змінено

### Списки тестів і сесій

- Основні дії видимі в рядку: запуск/редагування тесту та моніторинг сесії. Імпорт і додаткові дії зібрані в меню. Видалення відділене й потребує підтвердження.
- Пошук за назвою/предметом, для сесій також за кодом. Фільтри класу та статусу, лічильники основного списку/архіву. Українські назви в SQLite шукаються без урахування регістру.
- Активні сесії відображаються першими. Видно код, дату, клас і кількість завершених **спроб**: повторні проходження не видаються за окремих учнів.
- Зі списку можна копіювати посилання входу, керувати паузою/відновленням/завершенням усіх спроб, закріплювати сесію та закривати вхід. Закриття входу і завершення поточних спроб мають окремі назви й дії.
- Архівування/закріплення після виконання зберігають поточний пошук, фільтри та сторінку. Є адаптивне компонування для вузького екрана та меню з підтримкою Escape.
- Фільтрація і пагінація виконуються SQL-запитами. Лічильники питань/спроб обчислюються агрегатами лише для поточної сторінки. У перевіреній вибірці — не більше 7 SQL-запитів для тестів і 6 для сесій; колекції всіх питань і спроб не завантажуються для підрахунку.
- У редакторі кнопки збереження закріплено внизу під час прокручування, видалення прибрано з верхньої панелі.

### Надійність проходження

- Окремий кеш `localStorage` на кожну спробу: чернетки, незмінна черга надісланих відповідей, події з ID, пропущені питання, залишки браузерних таймерів, кількість порушень і намір завершення.
- Чернетки зберігаються при зміні відповіді. Перед запитом відповідь потрапляє в чергу; з черги вона видаляється лише після успіху. При втраті підтвердження однаковий повторний запит отримує успіх, відмінна відповідь на вже збережене питання — 409.
- Одночасні запити на збереження того самого питання об’єднуються на клієнті. Непідтверджену відповідь не можна змінити під час повторного надсилання. Перехід після таймера теж чекає на успішний запис.
- Завершення спочатку надсилає усі чернетки відповідей, зокрема на пропущені питання, решту черги та події. Намір завершення переживає розрив зв’язку. Якщо сервер завершив спробу, але підтвердження загубилося, клієнт перевіряє статус.
- Відновлення з’єднання має автоматичну перевірку та ручну кнопку; паралельні перевірки відновлення не запускаються. При недоступному сховищі повідомлення прямо пояснює, що дані залишаються лише у відкритій вкладці.
- Якщо вчитель зупинив спробу до надсилання відповіді, кеш не знищується й оцінка не переписується заднім числом. Можна завантажити локальний JSON для ручної перевірки; на сторінці завершення також є відновлення непідтвердженої копії. Автоматичного імпорту й гарантованої автентичності цієї копії немає.
- Браузерні таймери запускаються після входу у fullscreen, призупиняються при паузі/втраті зв’язку. Таймер питання не скидається через повторне відображення питання.
- Одне перемикання, що породило blur/visibility/fullscreen події, рахується одним попередженням. Вхід у тест, пауза й завершення не дають хибних порушень. Кількість порушень відновлюється в учня й моніторингу, повторне надсилання події з тим самим ID не збільшує її.
- Повторне проходження має окремий захищений endpoint, перевіряє налаштування/стан сесії й переносить ПІБ у нову спробу.

### Супутні виправлення

- Маршрути учня перевіряють підписану cookie і належність URL спробі. ПІБ без cookie більше не дозволяє забрати активну спробу. Учень без cookie направляється на учнівську сторінку входу.
- API та WebSocket перевіряють доступ до спроби/сесії; WebSocket перевіряє Origin і не видаляє нове підключення при відключенні старого. Неактивний учитель не може увійти.
- Сервер приймає відповіді лише на питання, призначені спробі, перевіряє тип/option ID/координати до запису. Невалідний запит не блокує подальшу правильну відповідь.
- У payload учня немає текстових еталонів, правильних пар, індексів правильного порядку й області hotspot. JSON із ключами пишеться в приватний `data/tests`, старий `/static/**/test.json` блокується. Старі фізичні файли та вже збережені копії в браузерах не видалялися.
- Локальні зображення в експорті обмежено коренем static та растровими форматами. Пряме завантаження перевіряє власника тесту, розмір до 10 МБ, розширення й сигнатуру; базові правила застосовано і до Base64-зображень JSON/XML. Це перевірка заголовка, не повне декодування зображення.
- JSON редактора передається через `tojson`, URL у змінених JS-шаблонах екрануються. Повний перегляд усіх джерел XSS/CSP не виконаний.
- Невідмічений checkbox показу результатів зберігає false. JSON-обмін тепер зберігає повторну спробу, часовий ліміт питання, шкалу, вибірку, виключені теми й налаштування перевірки. Перезапис предмета профілем при імпорті ще залишається.
- Оцінювання відповідей спроби використовує один commit замість commit на кожну відповідь. Персональні сторінки/API мають `Cache-Control: no-store`.
- Оновлено README, інструкцію користувача; приватні JSON виключено з Git і Docker build context.

## Перевірка

Команди відтворення:

```bash
.venv/bin/python tests/test_flows.py
node tests/student_sync.test.cjs
.venv/bin/ruff check --isolated --select E9,F63,F7,F82 app tests reports/audit_checks.py
git diff --check
```

- **12 інтеграційних тестів Python — пройдено.** Вісім типів питань, ідемпотентність/завершення, доступ HTTP/WebSocket, невалідні/непризначені питання, пауза, повторна спроба, лічильник/пропуски, приватні файли, пошук/архів/пагінація/кількість SQL-запитів, checkbox/JSON редактора, налаштування обміну, завантаження зображень.
- **13 сценаріїв JavaScript — пройдено у Node VM.** Ізоляція кешу, пошкоджений/недоступний storage, втрата підтвердження з reload, одночасне збереження, відхилення/таймер, дублювання порушень, порядок завершення, втрата його підтвердження, зупинка вчителем, робота таймерів/fullscreen, завершення з чернетками пропущених питань і відновлення локальної копії. Синтаксис шести змінених JS-файлів перевірено.
- Ruff перевірок синтаксичних/фатальних помилок і `git diff --check` — без помилок. `pip check` — залежності встановленого середовища узгоджені.
- Усі перевірки БД/файлів використовували тимчасові каталоги та вигадані дані. Робочі тести, учні, `.env`, резервні копії не змінювалися.

**Межі перевірки:** немає доступного браузера в інструменті перегляду, тому реальну верстку, drag-and-drop, fullscreen/мобільні браузери й мережевий сценарій у браузері не перевірено візуально. JS-перевірки використовують модель DOM/fetch. PostgreSQL, PyQt6 і навантаження класу не тестувалися. Перед шкільним запуском потрібен пробний тест на двох реальних пристроях із коротким відключенням мережі, паузою, reload і повторною спробою.

## Додаткова перевірка update/restore перед публікацією

За наступним дорученням користувача перевірено й виправлено `scripts/update.sh`, `restore.sh` та спільний `backup.sh`:

- Помилка Git, розходження гілки чи незбережені зміни припиняють оновлення; використовується тільки fast-forward у `main`.
- Захисний бекап обов’язковий. Застосунок зупиняється на час зняття PostgreSQL + файлів; `.env` не виконується як shell-код.
- До копії входять `data`, `static/tests`, `static/uploads`; manifest містить SHA-256 і версійні відомості.
- Архів перевіряється до зміни БД. Файли готуються через staging і замінюють старий вміст, із поверненням старих файлів при помилці перестановки. Legacy-копії підтримуються з попередженням.
- У Compose додано постійний том для `static/uploads`; update переносить зображення зі старого контейнера до нього до запуску нового.
- Попередній image зберігається під rollback-тегом. README розділяє відновлення даних і повернення коду/образу та містить конкретний приклад Compose override для rollback.
- Успіх визначається HTTP-готовністю. Помилка до запуску нового образу повертає старий контейнер; після початку заміни даних/розгортання застосунок залишається зупиненим із посиланням на захисну копію.
- Runtime-файли не включаються в Docker image; Dockerfile створює порожні каталоги для томів.

**15 тестів обслуговування пройдено:** перевірка checksum і небезпечних шляхів/посилань, точна заміна файлів, відкат помилки staging, legacy/перенесення uploads, помилки Git/бекапу/readiness/DB restore і успішні сценарії. Перевірено Bash-синтаксис і Compose-конфігурацію. Docker/Git у тестах замінено контрольованими заглушками; файли архівів і staging перевірялися реально в тимчасових каталогах.

Повне відновлення в PostgreSQL і реальну Docker-збірку/перезапуск ще треба перевірити на окремому стенді. Зовнішні клієнти БД/томів повинні припинити запис на час копіювання. Відома ревізія checkout у manifest може відрізнятися від ще запущеного image після ручного `git pull`; ID образу фіксується окремо.

Для одноразового контейнера використовуються томи сервісу за [Docker Compose run](https://docs.docker.com/reference/cli/docker/compose/run/). SQL-змінні передаються через stdin та екрановані psql literals/identifiers: [PostgreSQL 16 psql](https://www.postgresql.org/docs/16/app-psql.html). Відновлення dump зупиняється на помилках і виконується в одній транзакції: [pg_restore](https://www.postgresql.org/docs/16/app-pgrestore.html).


## Виправлення 1.1.1 після перевірки користувачем

Користувач повідомив, що Esc і зупинка після третього виходу не спрацювали. Перевірка коду виявила залежність обліку від станів `isViolationShowing`/`isOffline`, скидання попередження лише кнопкою повернення й відсутність серверного правила. Попередня JS-перевірка викликала `handleViolation` без послідовності справжніх подій, тому не покривала повернення через зовнішнє керування. Точний сценарій на серверному браузері не був відтворений.

- Спільний обробник standard/WebKit fullscreen та перевірка фактичних переходів усувають подвійний облік і відновлюють попередження при новому виході. Резервна перевірка працює кожні 500 мс. Esc, який браузер поглинає, фіксується як сам вихід; Esc без виходу не є порушенням.
- Третє порушення зупиняє спробу зі статусом `stopped` на сервері. Запис події, оцінка та журнал зупинки комітяться разом; запити збереження/завершення/події серіалізуються блокуванням запису спроби. Це не замінює решту рекомендованих міграцій і обмежень БД.
- Події виходів офлайн зберігаються локально. Після третього браузер не дозволяє продовжити, а журнал повторно доставляється. Чернетки заморожуються й надсилаються перед подією зупинки; якщо сервер їх не прийняв, локальна копія лишається для вчителя.
- Журнал доповнено доступними сторінці діями (зміна відповіді, клавіша Esc за наявності keydown, заблоковане копіювання/вирізання/контекстне меню, вставлення); події транслюються в моніторинг. Системні клавіші й дії в сторонніх застосунках сторінці недоступні.
- `app/version.py` — єдине джерело версії. Додано видиму 1.1.1, API/HTTP-заголовок версії, параметр версії в усіх локальних CSS/JS та CHANGELOG. Оновлення вже відкритих вкладок потребує reload перед початком тестування.

Перевірки цього виправлення: **15 інтеграційних тестів** на тимчасовій SQLite й **17 JS-сценаріїв**. Нові сценарії охоплюють три fullscreenchange без keydown, дубль WebKit/blur, повернення кнопкою та зовнішнім керуванням, офлайн/reload, пропущену подію, паузу вчителя, повторну доставку третьої події, конкурентні дублікати, зупинку лише одного учня та параметри версії. Ruff і перевірка whitespace пройдені.

Реальний браузер/Fullscreen API й PostgreSQL у цьому середовищі не перевірені; модель подій перевіряє логіку, а фактичні Esc, вигляд і серверне розгортання потрібно перевірити за сценарієм у README. Скрипти обслуговування в 1.1.1 не змінювалися; результати попередньої перевірки наведені вище.
