# 🎓 SchoolTest (ШколярТест) — Автономна система шкільного тестування

> **Повністю автономна, сучасна система для створення, проведення та аналізу тестування знань учнів у школі.**  
> Працює в локальній мережі без інтернету. Включає веб-платформу (FastAPI) та графічний GUI менеджер (PyQt6).


**Поточна версія: 1.4.2.** Історія випусків: [CHANGELOG.md](CHANGELOG.md).

### Версії та перевірка оновлення

Версія визначається в `app/version.py`, показується внизу сторінок вчителя та у верхній панелі тесту учня. `GET /api/version` повертає версію запущеного застосунку; HTTP-відповіді також містять `X-App-Version`. CSS/JS мають параметр цієї версії, щоб браузер отримував нові файли після оновлення. Для кожного релізу змінюйте `app/version.py` та додавайте запис у `CHANGELOG.md` (major — несумісні зміни, minor — нові можливості, patch — виправлення).

Оновлення на сервері з попереднього випуску:

```bash
./scripts/update.sh
curl -fsS http://127.0.0.1:8000/api/version
```

Очікувана відповідь — `{"version":"1.4.2"}`. Якщо використовуєте інший порт або адресу, підставте адресу свого сайту. Перед початком нових тестів оновіть уже відкриті сторінки учнів; код відкритої вкладки автоматично не замінюється.

### Відновлення запуску після помилки `No module named 'psycopg'`

У SQLAlchemy 2.1 драйвер для `postgresql://` змінився з `psycopg2` на `psycopg` ([офіційні зміни SQLAlchemy](https://docs.sqlalchemy.org/en/21/changelog/migration_21.html)). Образ 1.1.1 встановлював лише `psycopg2-binary`, тому нова збірка могла падати ще під час імпорту. У 1.1.2 встановлюються обидва драйвери та перевіряються під час збірки. Змінювати робочий `.env` для цього виправлення не потрібно.

Якщо update залишив контейнер зупиненим, у каталозі проєкту виконайте:

```bash
git pull --ff-only origin main
./scripts/update.sh
curl -fsS http://127.0.0.1:8000/api/version
```

Update працює й зі зупиненим контейнером: зробить захисну копію та збудує новий образ. Відновлювати БД через `restore.sh` для цієї помилки не потрібно. Якщо збірка не пройде, не запускайте старий несправний образ; перевірте повідомлення збірки. Помилка готовності тепер також автоматично виводить логи.

### Контроль режиму тестування у 1.1.1

- Вихід із Fullscreen API, зокрема через Esc, фіксується за фактичним переходом стану. Є також резервна перевірка стану кожні 500 мс. Натискання Esc без виходу саме по собі не збільшує лічильник.
- Вихід, приховування вкладки та втрата фокуса в межах одного попередження рахуються як одне порушення. Повернення у повний екран скидає попередження; наступний вихід рахується знову. Перші два попередження мають таймер повернення 10 секунд.
- Після третього порушення браузер блокує продовження, а сервер переводить **лише цю спробу** у `stopped`, виставляє результат за збереженими відповідями й повідомляє вчителя. Причину видно на сторінці завершення та в журналі. Повторна доставка тієї самої події не додає порушення.
- Під час втрати зв’язку виходи продовжують фіксуватися локально. Після третього продовжити тест не можна; сервер отримає журнал після відновлення мережі. Чернетки надсилаються перед подією зупинки, а непідтверджені відповіді залишаються для завантаження локальної копії. Під час паузи вчителя вихід записується як дія без штрафу.
- Журнал містить вхід, початок, зміни/збереження відповідей, переходи/пропуски питань, виходи й повернення, переключення вкладки/вікна, втрату/відновлення зв’язку, спроби копіювання/вирізання/контекстного меню, вставлення та завершення. Клавіша Esc записується окремо, якщо браузер передає її сторінці. Журнал показується в моніторингу та деталях результату.

Браузер дозволяє користувачу вийти через Esc ([MDN Fullscreen API](https://developer.mozilla.org/en-US/docs/Web/API/Fullscreen_API/Guide)); вебсторінка може виявити вихід і застосувати правило, але не заблокувати системні клавіші або спостерігати всі дії в ОС чи сторонніх програмах. Ліміт 3 збережено також для перемикання вкладок/вікон, як у попередніх правилах тестування.

Перевірка після розгортання: створіть короткий тест; увійдіть учнем; тричі натисніть Esc із поверненням до тесту після перших двох виходів. У моніторингу мають з’явитися 1 → 2 → 3, після третього — «Зупинено», а інший учень має продовжувати. Повторіть із коротким відключенням мережі та перевірте збережені відповіді.

## 🚀 Основні можливості (Feature Set)

### 📝 1. Підтримка 6+ типів питань
- **Одиночний вибір (`single_choice`)**: класичний вибір 1 правильного варіанта.
- **Множинний вибір (`multiple_choice`)**: вибір кількох правильних варіантів відповідей.
- **Вірно / Невірно (`true_false`)**: швидка оцінка тверджень.
- **Коротка текстова відповідь (`short_text`)**: введення слова або числа з нечітким порівнянням (Fuzzy Matching / Левенштейна) та нормалізацією пробілів і регістру.
- **Встановлення відповідностей (`matching`)**: інтерактивне з'єднання лівої та правої колонок (Drag & Drop та спадні списки).
- **Встановлення послідовності (`sequence`)**: зручне сортування етапів чи подій за порядком.
- **Графічні питання та вибір зображень (`image_choice` / `hotspot`)**: додавання ілюстрацій до тексту питань та варіантів.

### 📥 2. Універсальний імпорт тестів
- **Імпорт із Microsoft Word (`.docx`)**: автоматичне розпізнавання питань, варіантів відповідей, виділених правильних варіантів (зелений колір / жирний шрифт) та завантажених зображень.
- **Імпорт MyTestX XML (`.xml`)**: повна сумісність із популярним шкільним форматом MyTestX (розпізнавання розділів, питань та варіантів).
- **Імпорт та експорт у JSON**: швидкий обмін тестами між викладачами та різними ПК.

### 🔍 3. Інтелектуальна перевірка та Вікно аналізу помилок у тестах
- **Динамічний аналіз у реальному часі**: виявлення повторень варіантів відповідей у межах одного питання.
- **Модальне вікно `🔍 Вікно помилок`**: швидкий фільтр за типами помилок, пошук, кнопки **«🎯 Перейти до питання»** (з підсвічуванням та плавним скролом) та **«🗑️ Видалити це питання»** (із підтримкою скасування дії через `Ctrl+Z`).
- **Наочні підказки**: яскравий баннер прямо всередині картки питання вчителя.

### 🎨 4. Динамічне оформлення та перемикач теми
- **Сучасний дизайн (Glassmorphism & Vibrant Palette)**: адаптоване оформлення для будь-якої роздільної здатності.
- **Перемикач теми (Light / Dark Mode)**: стильна кругла плаваюча кнопка у правому верхньому кутку на всіх сторінках вчителя та учня з динамічною зміною вигляду.
- **Індикатор завантаження (`TopLoader`)**: плавний верхній прогрес-бар при збереженні та навігації між сторінками.

### 📡 5. Моніторинг у реальному часі (WebSocket)
- **Монітор проходження**: викладач бачить прогрес учнів у реальному часі (зелені/червоні квадратики відповідей, статус та бали).
- **Керування сесією**: можливість ставити на паузу, відновлювати чи достроково завершувати тест для окремого учня або всього класу.

### 🛡️ 6. Захист від списування, фіксація спроби та Безпека
- Контроль повноекранного режиму (виявлення перемикання вкладок/вікон).
- Блокування копіювання тексту та виділення.
- **Детерміноване перемішування питань і варіантів відповідей**: порядок фіксується окремо для кожної спроби учня та гарантовано не змінюється при перезавантаженні сторінки (F5).
- **Захист від повторної здачі збережених відповідей**: збережені відповіді блокуються на сервері (HTTP 400) та усуваються з черги проходження, що унеможливлює повторне перебирання варіантів через оновлення сторінки.
- Логування подій браузера (відкриття/закриття, втрата фокусу).
- **Захист відповідей при втраті зв’язку**: чернетки та черга надсилання зберігаються окремо для кожної спроби на пристрої учня. Однаковий повторний запит безпечно підтверджується сервером; завершення чекає на збереження відповідей.
- **Повторне проходження**: якщо дозволено вчителем і сесія відкрита, нова спроба використовує збережене ім’я учня.
- **Зручні списки вчителя**: пошук за назвою/предметом/кодом, фільтри класу та статусу, активні сесії першими, основні дії в рядку й додаткове керування в меню.

Браузер дозволяє учню вийти з fullscreen через Esc; застосунок фіксує вихід, показує попередження та відлік. Для суворого блокування потрібен керований режим кіоску на шкільному ПК. Продовжувати спробу слід у тому самому браузері зі збереженими cookie; одного ПІБ недостатньо для доступу.

## 💻 Запуск системи

### 🔹 На Windows:

1. **Автоматичне налаштування середовища**:
   Запустіть `setup_env.bat` (автоматично створить `.venv` та встановить усі бібліотеки).
2. **Запуск графічної панелі керування**:
   Запустіть `run_gui.bat` або `start_windows.bat`.
3. **Вікно реєстрації користувачів**:
   Запустіть `start_register.bat` або натисніть кнопку **«👥 Користувачі / Реєстрація»** у головному GUI вікні.

### 🔹 На Linux:

1. **Запуск сервера**:
   ```bash
   chmod +x start_linux.sh
   ./start_linux.sh
   # або вручну:
   python3 run.py
   ```
2. **Запуск вікна реєстрації (PyQt6)**:
   ```bash
   python3 run_register.py
   # або:
   ./start_register.sh
   ```

## 🔑 Перший запуск та створення адміністратора

При першому запуску сервісу, якщо в базі даних ще немає жодного користувача:
1. **Веб-майстер початкового налаштування (`/setup`)**:
   - Перейдіть у браузері за адресою `http://localhost:8000/` (або `http://localhost:8080/` у Docker).
   - Система автоматично перенаправить вас на сторінку **`/setup`** для створення головного облікового запису адміністратора.
   - Вкажіть ПІБ, логін, надійний пароль, предмет та класи.
   - За бажанням відмітьте чекбокс **«Завантажити зразковий тест»** для швидкого ознайомлення з можливостями.
   - Після створення адміністратора сторінка `/setup` блокується з міркувань безпеки.
2. **Через графічне вікно реєстрації (PyQt6)**:
   - Запустіть `start_register.bat` (Windows) або `python3 run_register.py` (Linux).
   - Створюйте та редагуйте облікові записи вчителів безпосередньо у зручній таблиці.

## 🐳 Розгортання з Docker та PostgreSQL (Production)

Для розгортання в production-середовищі рекомендується використовувати Docker. Це забезпечує ізоляцію, легке оновлення, резервне копіювання та перенесення між серверами. У цьому режимі замість SQLite використовується **PostgreSQL**.

### Вимоги

На сервері або ПК мають бути встановлені:
- [Docker](https://docs.docker.com/get-docker/)
- [Docker Compose](https://docs.docker.com/compose/install/)
- Для скриптів обслуговування: Bash, Git, Python 3.9+ і tar. Вони запускаються з Linux-сервера.

### Покрокове розгортання

1. **Клонуйте репозиторій з GitHub**:
   ```bash
   git clone https://github.com/yrskrs/school_test.git
   cd school_test
   ```

2. **Створіть файл конфігурації `.env`**:
   ```bash
   cp .env.example .env
   ```

3. **Налаштуйте параметри у `.env`**:
   Відкрийте `.env` у текстовому редакторі (`nano .env`) та задайте:
   - `APP_PORT` — зовнішній порт веб-сервера (за замовчуванням `8000`).
   - `POSTGRES_PASSWORD` — надійний пароль для бази даних.
   - `DATABASE_URL` — оновіть пароль відповідно до `POSTGRES_PASSWORD`.
   - `SECRET_KEY` — згенеруйте випадковий секретний ключ для підпису сесій.

4. **Запустіть систему в Docker**:
   ```bash
   docker compose up -d --build
   ```

5. **Перевірте стан контейнерів**:
   ```bash
   docker compose ps
   ```

6. **Початкове налаштування в браузері**:
   - Відкрийте `http://<IP_АДРЕСА_СЕРВЕРА>:8000/` (або вказаний `APP_PORT`).
   - Система автоматично перенаправить вас на **`/setup`** для створення облікового запису адміністратора.

> [!NOTE]
> База даних PostgreSQL працює в окремому контейнері `postgres`. Всі її дані зберігаються у Docker-томі `postgres_data`. Файли користувачів (тести, результати, завантажені зображення) зберігаються у томах `app_data`, `app_uploads` і `app_general_uploads`. Видалення контейнерів не видаляє ці томи; `docker compose down -v` видаляє дані, тому для звичайного оновлення цю команду не використовуйте.

### 💾 Резервне копіювання (Backup)

```bash
./scripts/backup.sh
```

Скрипт тимчасово зупиняє застосунок, знімає PostgreSQL dump і копії `data`, `static/tests`, `static/uploads`, після чого повертає попередньо запущений застосунок. Це потребує короткого вікна обслуговування: не запускайте під час тестування. Інші клієнти, що пишуть безпосередньо в PostgreSQL/томи, також мають припинити запис.

Копія зберігається у `backups/<дата-час>-<унікальний-суфікс>/`:

- `database.dump` — PostgreSQL custom-format dump;
- `files.tar.gz` — файлові сховища, включно з приватними JSON тестів;
- `manifest.json` — SHA-256, час UTC, Git-ревізія робочого checkout і ID фактичного образу контейнера. Після ручного `git pull` checkout може бути новішим за ще запущений образ.

Невдала копія не має валідного manifest і не повинна використовуватися. `.env` не включено: його та резервні копії потрібно окремо захищати й переносити тільки довіреним каналом.

### 🔄 Відновлення (Restore)

Відновлення замінює поточні дані. Перевірте шлях до копії та сумісність версії застосунку.

```bash
./scripts/restore.sh backups/ВАША_КОПІЯ
# Без інтерактивного підтвердження:
./scripts/restore.sh backups/ВАША_КОПІЯ --yes
```

Перед змінами перевіряються checksum, формат dump, gzip та всі шляхи архіву. Посилання, спеціальні файли й вихід за межі дозволених каталогів відхиляються. Потім створюється обов’язкова захисна копія; її помилка припиняє відновлення **до заміни БД**.

Файли спочатку готуються у staging-каталогах у томах, потім замінюють їх попередній вміст: зайві файли не залишаються. Застосунок запускається лише після успішного відновлення БД/файлів; успіх підтверджується HTTP-запитом із контейнера. При помилці після початку заміни даних застосунок залишається зупиненим, а скрипт друкує шлях захисної копії.

Старі копії без `manifest.json` підтримуються з попередженням: у них немає checksum/версії. Якщо старий архів не має `uploads`, цей том зберігається без заміни.

**Restore відновлює дані, а не Git-код або образ автоматично.** Використовуйте сумісну версію застосунку; повернення попереднього образу описано нижче.

### 🚀 Оновлення системи (Update)

Для **першого оновлення з попередньої версії скриптів** спочатку отримайте нові скрипти, залишивши старий контейнер працювати:

```bash
git pull --ff-only origin main
./scripts/update.sh
```

Надалі достатньо:

```bash
./scripts/update.sh
```

Потрібні гілка `main` і чисте робоче дерево. Скрипт:

1. Отримує `origin/main` і перевіряє можливість fast-forward; помилка Git припиняє оновлення.
2. Зберігає попередній образ під тегом `schooltest-rollback:<назва-копії>`.
3. Зупиняє застосунок і створює узгоджений захисний бекап усіх сховищ.
4. Оновлює код тільки через fast-forward і збирає образ.
5. Переносить загальні зображення зі старого контейнера в новий постійний том `app_general_uploads`.
6. Запускає застосунок і перевіряє HTTP-готовність, включно з доступом до БД. `READY_TIMEOUT=180 ./scripts/update.sh` змінює типовий ліміт 90 секунд.

До запуску нового контейнера помилка повертає попередній контейнер. Після початку розгортання помилка залишає застосунок зупиненим: автоматично запускати старий код поверх потенційно зміненої БД небезпечно. Шлях бекапу й тег попереднього образу друкуються в консолі. Не видаляйте rollback-образ до завершення перевірки.

> [!NOTE]
> Якщо контейнер застосунку ще не створено (новий сервер або після `docker compose down`), `update.sh` зупиняється з повідомленням про відсутність контейнера (`App container is missing; use initial deployment instead`). Для першого створення контейнерів виконайте початкове розгортання: `docker compose up -d --build`.

### ⏪ Повернення до попередньої версії (Rollback)

Для повного повернення потрібні **і попередній образ, і дані з відповідної копії**. `update.sh` зберігає обидва локально. Підставте точні назви, надруковані скриптом:

```bash
cat > /tmp/schooltest-rollback.yaml <<'YAML'
services:
  app:
    image: schooltest-rollback:НАЗВА_КОПІЇ
YAML
COMPOSE_FILE=compose.yaml:/tmp/schooltest-rollback.yaml ./scripts/restore.sh backups/НАЗВА_КОПІЇ
```

Перевірте наявність образу через `docker image inspect schooltest-rollback:НАЗВА_КОПІЇ`. Override обирає попередній образ для відновлення й запуску. Git checkout залишається на поточній ревізії. Самого `restore.sh` без вибору сумісного образу недостатньо для повернення коду.

### 🚚 Перенесення на інший сервер / ПК

1. На старому сервері створіть копію: `./scripts/backup.sh`.
2. Перенесіть копію й `.env` безпечним каналом. На новому сервері підготуйте репозиторій сумісної версії та Docker. `.env` має містити відповідні PostgreSQL DB/user/password і `DATABASE_URL`.
3. Зберіть образ та відновіть дані:

```bash
docker compose build app
./scripts/restore.sh backups/ВАША_КОПІЯ
```

Скрипт запускає PostgreSQL, чекає готовності й створює контейнер застосунку, якщо його ще немає. Локальний rollback-тег самостійно між серверами не переноситься: для нього потрібні `docker image save/load` або збірка сумісної версії.

### ✅ Перевірка цього оновлення на сервері

Після отримання коду та виконання `update.sh`:

1. Перевірте `docker compose ps` і `docker compose logs --tail=100 app`.
2. Увійдіть учителем, перевірте пошук українською, фільтри класу/статусу, запуск тесту й меню керування сесією.
3. Пройдіть короткий тест учнем, перемкніть вікно, поверніться у fullscreen і перевірте лічильник у моніторингу після оновлення сторінки.
4. Під час надсилання відповіді ненадовго відключіть мережу учня. Після відновлення перевірте збереження відповіді без дубля та продовження таймерів.
5. Перевірте повторне проходження без введення ПІБ і приховування результату, коли його вимкнено в налаштуваннях.
6. Перевірте старі/нові зображення та результати. Повний пробний restore виконуйте в окремому Docker-проєкті, а не поверх робочих даних.

Локально пройшли 12 інтеграційних тестів застосунку, 13 сценаріїв JS та 15 перевірок архівів/скриптів. Docker-команди в тестах скриптів змодельовано; реальний PostgreSQL restore, Docker rebuild і перевірку у браузері необхідно виконати на сервері/стенді.

### 🔀 Міграція з існуючої SQLite на PostgreSQL

Якщо ви раніше користувалися системою через локальний SQLite і хочете перейти на Docker + PostgreSQL без втрати даних, виконайте наступні кроки:

1. Запустіть інфраструктуру в Docker: `docker compose up -d`
2. Переконайтесь, що ваш старий файл бази лежить за шляхом `data/school_testing.db`.
3. Запустіть скрипт міграції:
   ```bash
   python scripts/migrate_sqlite_to_postgres.py
   ```
   Скрипт автоматично прочитає дані зі SQLite та безпечно перенесе їх у PostgreSQL у контейнері.

### Підключення за IP та незалежний вхід

Створіть **ключ API** у тестах або завданнях. У журналі відкрийте **«Підключити тести / завдання»**, вставте **адресу джерела з IP і портом** та **ключ** у два окремі поля. JSON вводити не потрібно. Виберіть назви класу/предмета та підтвердьте учнів. Після зміни IP відкрийте це саме підключення й змініть адресу: учні й імпортовані оцінки збережуть прив’язки. Джерело має бути доступне серверу журналу; різні LAN потребують маршруту або приватного VPN. Коли зв’язку немає, локальні дані та основна робота залишаються доступні.

Журнал і завдання використовують окремі cookies сесії та CSRF. Чинна власна стара сесія переноситься автоматично. Якщо її вже перезаписав інший сайт або ви відкрили сайт за іншою IP-адресою, увійдіть один раз. Після оновлення перезавантажте відкриті вкладки для отримання нового JavaScript.
