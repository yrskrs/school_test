# Продовження призупинених спроб — 1.6.5

Дата перевірки: 2026-10-15. Зміни доповнюють наявний механізм відповідей, паузи та локального відновлення.

## Порядок роботи

1. Учитель ставить окремого учня або всіх учнів на паузу, залишаючи сесію відкритою. Завершення спроби та закриття входу до сесії — окремі дії.
2. Учень відкриває те саме посилання або код на будь-якому пристрої та обирає власне ім’я. Для списку класу пошук спроби використовує ID учня; для ручного входу — нормалізоване ім’я в цій сесії.
3. Учень натискає «Продовжити тест», вмикає повноекранний режим і бачить паузу. До команди вчителя відповідати не можна, таймери не зменшуються.
4. Після відновлення повертаються поточне питання, черга питань, пропуски, збережені відповіді, серверні чернетки та залишки загального часу й часу окремого питання. Нове проходження не створюється.
5. Перенесення змінює підписану сесію браузера: попередній браузер не може перезаписати прогрес. Повернення після випадкового закриття вкладки на тому самому пристрої зберігає локальне відновлення; повторний вхід після закінчення cookie також може використати локальний стан попереднього входу.

## Імена та зміна місць

Відповіді належать конкретній спробі учня, а не комп’ютеру, місцю, користувачу ОС чи профілю браузера. Петро за комп’ютером Олени обирає Петра й отримує спробу Петра; Олена за комп’ютером Петра обирає Олену й отримує спробу Олени. Локальна копія з іншого ID спроби не підставляється.

Код і вибір імені не підтверджують особу паролем. Той, хто навмисно вибере чуже ім’я, може відкрити чужу призупинену спробу. Цей випуск не додає окремих паролів або PIN учнів.

## Наявні паузи та база даних

- Під час запуску автоматично додається nullable JSON-поле `student_attempts.progress_state`. Оновлення повторюване; старі спроби, відповіді та оцінки не видаляються.
- Для спроб без нового поля використовуються збережені відповіді, детермінований порядок питань та журнал подій. Загальний час обчислюється без інтервалів між паузами й відновленнями; остання відкрита пауза також не витрачає час.
- Якщо старий журнал не містить події паузи, точний початок паузи встановити неможливо; використовується остання записана активність без списання всіх днів очікування.
- Чернетку й точний час окремого питання, які до цього випуску існували лише локально, неможливо відновити на іншому ПК без старого браузера. Відкрийте призупинений тест у тому браузері після оновлення та дочекайтеся збереження прогресу на сервері.
- Новий клієнт передає прогрес після змін, періодично раз на 5 секунд, при отриманні паузи й при закритті вкладки. Без зв’язку доступний лише останній переданий серверний стан; локальна копія залишається на пристрої.
- Активна спроба без паузи продовжується з чинною cookie того самого браузера. Для перенесення спочатку потрібна пауза вчителя. Закрита сесія не дозволяє новий вхід.

## Виконані перевірки

Усі дані синтетичні, бази тимчасові. Робочу БД, учнів і результати не змінювали.

- **130 Python-перевірок застосунку**: збереження та оцінювання відповідей, права доступу, ліміти проходжень, списки, імпорт/експорт, оновлення й міграції. Серед них 7 нових сценаріїв прогресу та перевірка доповнення старої схеми з паузою.
- **22 перевірки протоколу обміну**: попередня поведінка обміну й сталих ID збережена.
- **22 JavaScript-сценарії**: локальна черга, втрачене підтвердження, офлайн, fullscreen, пауза, відновлення позиції та таймерів, перенесення й повторний вхід після закінчення cookie. Додатково перевірено синтаксис 7 скриптів.
- **Chromium, дві незалежні cookie/localStorage-сесії**: вибір учня зі списку; fullscreen перед екраном паузи; перенесення спроби з чернеткою та порядком; відкликання доступу старого браузера; продовження обох таймерів учителем; спільна пауза; перезавантаження зі збереженням стану. JavaScript-помилок немає.
- **Статичні перевірки**: новий сервіс і Python-сценарії проходять Ruff; `git diff --check` не виявляє помилок.

Команди для повторення автоматичних перевірок:

```bash
.venv/bin/python -m unittest discover -s tests -p 'test_*.py'
.venv/bin/python -m unittest discover -s school_sync/tests
node tests/student_sync.test.cjs
```

Нові серверні та браузерні сценарії перевірено з SQLite. Повторну збірку Docker і запуск цих сценаріїв із PostgreSQL у цьому випуску не виконували. Записи цього звіту описують перевірку коду, а не розгортання на робочому сервері.
